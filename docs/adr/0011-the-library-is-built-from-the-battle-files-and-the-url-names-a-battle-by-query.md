v0.1 plays one battle: `?battle=<name>` on the URL, `trafalgar` when the parameter is missing, and nothing else on the site. v0.2 holds four, so the site needs a front door. We decided that the **library** is the front door: the bare site URL (`/sandtable/`) lists every battle oldest first by title, date and summary, and a battle plays at the same page with `?battle=<name>`. The list is **generated by the build from the battle files** in `data/battles/`, never hand-written, so a battle joins the library by existing. The player gains a **picker** in its controls that navigates to another battle as a fresh visit. There is no default battle and the site remembers nothing.

## Considered options

- **A hand-written index file** listing each battle's name, title, date and summary. Rejected: it drifts from the files, and every new battle is written twice. The battle file is already the one place a battle describes itself (`title`, `date`), and `npm run validate` already walks every file, so the build can walk them too.
- **Fetching every battle file at runtime** and reading its header. Rejected: the library would download every phase list to show four titles, and the cost grows with the library.
- **Pretty paths** (`/sandtable/trafalgar/`). Rejected for v0.2: GitHub Pages serves static files only, so a path needs either an `index.html` emitted per battle by the build or the `404.html` routing trick, which answers a 404 status to crawlers and link previews. The query parameter already works and shares cleanly. Per-battle copies of the page can be emitted later without changing what the app reads.
- **A hash** (`/sandtable/#trafalgar`). Rejected: invisible to link previews and analytics, and it reads as an anchor.
- **A picker only, no library page**, the player opening on a default battle. Rejected: a battle deserves room to describe itself, the site deserves a face, and a bare link should show the choice rather than one battle chosen for the viewer.
- **Two HTML pages**, one for the library and one for the player. Rejected: nothing today needs a second document; the entry script branches on the parameter, and the design-language work sets the library's look inside the same page.
- **Swapping battles in place** from the picker, keeping player state. Rejected: a full navigation keeps the URL truthful, needs no teardown path in the player, and the speed multiplier is already defined as per-visit.
- **Remembering the last battle** in browser storage. Rejected: the library is one click away, so there is nothing to remember.

## Consequences

- **The battle file gains `summary`**, one plain sentence, required in schema v2. It is the file's own description of the battle and is shown wherever the battle is named but not played.
- **The library is chronological**, oldest first, so it reads as a timeline. That needs a machine-readable date the file does not yet carry; the battle-clock decision (which is settling how the Nile's second day is written) supplies it, and this ADR only requires that a sortable date exists in v2 and the build sorts on it.
- **The build emits `data/index.json`** from the battle files, carrying for each battle its name, title, date, sort date, summary and the side names its units use. It is a build output, never committed, and the dev server generates it the same way so `npm run dev` shows the library too.
- **Sides are derived from the units** for now. Whether a battle file gets a `sides` block naming and ordering each side is the unit-types and hierarchy tickets' call.
- **No thumbnails in v0.2.** A rendered still needs the renderer at build time and a decided view to render; it stays in the fog.
- **The library page also carries the site's name, its one-line idea, and a credit line** with the repository link and the data licence.
- **An unknown battle name** keeps the load-error notice, with a link back to the library.
- **Grouping the library** (by commander, campaign, era) is out of scope until the list is long enough to need it.
- **Only battles live in `data/battles/`.** The library offers every file there, so a file there is a promise to a visitor: a real battle, researched against its sources, with a summary that describes the battle rather than the file. Something battle-shaped that exists to exercise the code is a **fixture**, and fixtures already have a home — `src/app/fixtures.ts`, played at `?fixture=<name>`, never fetched and never listed. That keeps the rule above whole: nothing on the front door is there by accident, and no field on a battle has to say which kind it is.
