# The product is renamed from Sandtable to Marchpast

The v0.3 map ([#121](https://github.com/NullCoderException/marchpast/issues/121)) carried "Sandtable stays unless the name research finds a conflict" as a standing condition, because a brand ticket was about to draw a logo, a favicon, an icon set, a social card and a library masthead, and a task ticket was about to buy a domain. The name research ([#125](https://github.com/NullCoderException/marchpast/issues/125)) found the conflict. **Sandtable, Inc.** filed USPTO application **99925941** for the standard-character mark SANDTABLE on 2026-07-07 in classes **9 and 42**, for software that plans, simulates and rehearses missions over terrain; **SIMTABLE** was *registered* in the same classes three months earlier (reg. 8220332, 2026-04-21); a third company, Virtual Sandtable LLC, trades on the word in the same field; the `sandtable` package on npm has five releases from 2026 and a live maintainer; and of the useful domains only `sandtable.dev` is free.

We decided to **rename the product to Marchpast**, and to land the rename in **two waves**: every user-visible string and document heading with the v0.3 build, and the repository name together with the Pages base path when the custom domain goes live.

## Considered options

- **Hold "Sandtable" as a working title on `sandtable.dev`**, and revisit if a store listing is ever refused. Rejected on cost curve rather than on risk. The next two tickets on the map draw a logo and buy a domain, so the price of the rename rises from a string sweep to a redraw the moment either lands; this is the cheapest hour the rename will ever cost. And holding means building a brand on a word we could never register, that three simulation-software companies already use for software that animates forces over terrain, one takedown request from a store listing.
- **A qualifier: "Sandtable Battles", "Sandtable History".** Rejected on the research's reading: 99925941 is a *standard-character* mark for the same word, in the same classes, for the same subject matter, so a qualifier does not separate us from it.
- **Battleplot.** The most discoverable of the three candidates, because it says exactly what the app is, and `.app`, `.dev` and `.com` are all free. Rejected as the least ownable: it enters a crowded field of live PLOT marks in classes 9 and 42 (High Alpha, Plot Technologies, Plotline Travel), so a later registration could draw a citation. "Plot" is also ambiguous between a graph and a scheme, which drags the name toward charting libraries rather than battles.
- **Plotting Room.** The best *fit* of any candidate considered: a wartime naval plotting room is a table, counters and arrows moved by hand, which is very close to what this renderer draws. Rejected on three counts that all outlast the metaphor. It is two words, which is worse everywhere a wordmark, a domain or a package name is wanted; `plottingroom.com` was registered in May 2026, so the set of free domains is already broken; and it shares ROOM with a live class 9/42 collaboration-software mark.
- **A fresh candidate, checked to the same depth.** Not pursued. Three were already checked across npm, `.app`, `.dev`, `.com`, both app stores, USPTO and TMview, and one of them is clean in every register at exact match. The research also records five names dropped along the way (Fieldglass, Warplot, Orrery, Cartouche, Vedette), so the shortlist was not thin.

## Consequences

- **Marchpast is ownable.** Zero hits at exact match in USPTO, in TMview across all offices, in the WIPO Global Brand Database, on npm and in either app store, and `marchpast.app`, `.dev` and `.com` were all free at list price on 2026-09-07. It is an ordinary English noun, which reads as weakly distinctive, but it is *arbitrary* as applied to battle-playback software, and an arbitrary mark is the strong kind.
- **The name teaches nothing, and neither did the old one.** The phrase "sand table" appears nowhere in this repo's prose: not in the README, not in `docs/CONCEPT.md`, not in `CONTEXT.md`. The whole explanation is carried by the README's first sentence and the library masthead's idea line, and it stays there. So the rename costs no prose, and the masthead line, which the brand ticket owns, is now the only thing that says what the app is.
- **The glossary is a one-line change.** "Sandtable" is the heading of `CONTEXT.md`, not a defined term; no entry in its Language section names the product. Renaming the product does not touch the domain model.
- **Wave one, with the v0.3 build.** The `<title>` in `index.html`, the library masthead and its GitHub link text in `src/app/libraryPage.ts`, the document-title suffix and console prefixes in `src/main.ts`, the error prefix in `vite/library.ts`, `package.json`'s `name`, and the headings of `README.md`, `CONTEXT.md`, `CLAUDE.md` and `docs/CONCEPT.md`. All of it is string work with no path change, so the live Pages URL keeps serving throughout.
- **Wave two, with the domain task.** The custom domain makes the Pages base a bare `/`, at which point the `/sandtable/` literal in `vite.config.ts` and in the three test files that assert it is **deleted rather than rewritten**, and the repository is renamed after that. Renaming the repository first would rewrite that literal twice, once to the new repository name and again to a slash when the domain lands, and would break the `github.io` URL in between for no gain. This ordering is what GitHub itself recommends: a rename redirects "all existing information, with the exception of project site URLs", and [GitHub's own guidance on renaming a repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/renaming-a-repository) says that if you plan to rename a repository that has a Pages site, use a custom domain first, because that "ensures that the site's URL isn't impacted by renaming the repository". So the domain is not merely convenient before the rename, it is the thing that makes the rename free.
- **The CC BY attribution string changes.** "Sandtable contributors, CC BY 4.0" is the credit this project *asks* downstream reusers to give, and it stands in four battle files, three map files, `src/schema/examples.ts`, `src/timeline/testBattle.ts` and the `docs/schema.md` example. Every one is rewritten to name Marchpast, and `data/LICENSE` gains a line recording that the project was called Sandtable until 2026-09-07. The copyright holders are the same people before and after; CC BY 4.0 asks for attribution in the manner the licensor requests, and the licensor is restating the request. Nothing already reused under the old string is invalidated, and the licence note lets anyone holding an old copy trace the credit forward.
- **"(working title)" goes.** `docs/CONCEPT.md` has carried the qualifier in its heading since v0.1. The name has now been checked in six registers and chosen, so the qualifier would be false; the rename becomes a line in that document's decisions log instead.
- **`docs/adr/` is not swept.** ADR-0009 to ADR-0019 mention the old name in prose and in path examples such as `/sandtable/trafalgar/`, and their issue links point at the old repository path. An ADR records what was decided when it was decided, so the string sweep leaves the directory alone apart from this file. The old issue links keep resolving because a rename redirects issues, and every `git clone`, `fetch` and `push` against the old location keeps working, per [GitHub's own guidance on renaming a repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/renaming-a-repository).
- **The domain task is gated on this decision and nothing else.** It was never waiting on the logo: no part of the brand affects which domain is bought. The three Marchpast domains together cost about USD 29 for the first year at list price, they were unregistered on 2026-09-07, and every day they stay that way is a day one of them can go. The `marchpast` npm name was free the same day and is worth reserving alongside them.
- **The name `NullCoderException/sandtable` must never be reused.** [GitHub's own guidance on renaming a repository](https://docs.github.com/en/repositories/creating-and-managing-repositories/renaming-a-repository) warns that creating a new repository under the account with the renamed repository's original name permanently breaks every redirect to it. So the old name is not to be parked, squatted defensively, or re-created as an archive or a redirect stub: doing that would silently kill the redirects that ADR-0009 to ADR-0019, this map's tickets, and every external link to the project rely on. Leaving the old name unused is what keeps them alive.
- **`package.json` is `"private": true`,** so the package name collides with nothing today and the rename of that field is cosmetic until the project ever publishes.

## Correction, 2026-09-07

The consequence above says the old issue links keep resolving "because a rename redirects issues". **They do not.** Tested anonymously within minutes of the rename: the repository root, `/pull/146` and `/blob/main/README.md` all redirect from the `sandtable` path to the `marchpast` one, and the REST API follows the rename too — but every `/issues/<n>` under the old path returns **404**, checked across #1, #36, #121, #136, #142 and #146, each of which answers 200 under the new path.

So the thirty old-path links in this directory and in `docs/schema.md` were dead the moment the repository was renamed. They are rewritten to the new path in the same change as this note, which is the only edit the rename makes to `docs/adr/`: the prose still records what was decided when it was decided, and only the link targets move.

If GitHub's issue redirect is merely slow to propagate rather than absent, the rewrite cost nothing, since the new path is the canonical one either way. The rest of that consequence stands: `git clone`, `fetch` and `push` against the old location keep working, and the warning against ever reusing the name `NullCoderException/sandtable` stands unchanged — it is what keeps the redirects that *do* work alive.
