# A view reaches the player surface, and the viewer's choice is remembered

*Amended 2026-09-07 on [#160](https://github.com/NullCoderException/marchpast/issues/160): the surface takes `forced-color-adjust: none`, so it keeps the view's inks in Windows High Contrast rather than being repainted in system colours around a canvas that cannot follow. The derivation below is otherwise unchanged, and `color-scheme` is still **set** from the paper's luminance rather than **read** from the operating system — the site reads no user-preference media query at all (**ADR-0029**).*

ADR-0014 decided that **the view stops at the canvas edge**: the controls stay in the chart plate's language whatever view is picked, and no palette value reaches CSS. It gave two reasons. The first was that a view is a treatment of the *picture*, so a screenshot of the canvas is still the whole view. The second was that making the controls follow would oblige every future view to supply control-legible values as well as plate values.

Both have expired. The first is already false: the phone's Details panel carries the plate's key as one small canvas per row, drawn in the view's own glyph and pens ([#86](https://github.com/NullCoderException/marchpast/issues/86)), so the view crossed the canvas edge a version ago. The second rests on a premise the code disproves — `player.css` sets `--st-ink: #2b2418`, `--st-parchment: #efe3c6` and `--st-sunk: #e3d3ac`, which are exactly `CHART_PLATE.palette.ink`, `.paper` and `.land`, under a comment saying they are "copied rather than published". A view already supplies every value the surface needs; it just publishes none of them, and the same four values are hand-copied into `player.css`, `library.css` and `index.html`'s inline `<style>`.

Theming is the product goal for v0.3, so the controls follow the picture. Decided on [#127](https://github.com/NullCoderException/marchpast/issues/127).

## Considered options

- **A `surface` slot on `View`**, a table of control-legible colours each view supplies. Rejected on ADR-0021's own rule: *a fifth slot is cut for a view that exists, never for one that might.* The slot would be cut for the staff map, which has not been drawn, and the three views that do exist need nothing in it — every token the strip uses is already `ink`, `paper` or `land`.
- **Extra keys on the palette** — `control`, `controlText`, `trough`. The same objection, and it puts control values in a table that has only ever held picture values, so the palette stops being answerable by looking at the plate.
- **A `data-view` attribute and a stylesheet block per view.** Rejected: it makes every new view cost a CSS block that re-copies colours already in `views.ts`. That is the hand-copy problem this decision exists to end, made permanent and given a fourth site.
- **A stylesheet per view.** The same, with the copies further apart.
- **Writing the custom properties every frame**, beside the rest of `update`. Rejected: nine property writes and a style recalculation at sixty frames a second, for values that change only when the viewer picks a different view.
- **One face for ever, only colour following the view.** Genuinely arguable — the strip is closer to app chrome than to the picture, and a fixed face never reflows. Rejected on the page: an engraved serif strip under a sans operations map reads as two applications bolted together, which is the opposite of what a theme is for. ADR-0021's rule that a switch *waits* until its face resolves already means the reflow never happens in the wrong face.
- **The surface taking the view's type sizes as well as its face.** Rejected: the strip's sizes are set by hit targets — 36 pixels on a phone — and by what fits before the strip wraps and eats the plate's height. None of the eight fixed type roles is a button.
- **A `&view=` parameter on the URL**, so a look is shareable. Rejected for now: it does not survive the library's links, which are `?battle=<name>`, so it would have to be threaded through the Picker and every library entry to work at all. It can be cut later, against someone actually wanting to share a look.
- **Remembering the level and the speed too.** Rejected for two different reasons. A level is a reading depth *of one battle* whose names differ per battle, so a global one is meaningless and a per-battle one is a structure nobody asked for; and ADR-0017's "every visit opens on the coarsest" is an honesty rule, not a convenience. The speed is transport state, like the clock and the play flag.
- **The storage read and write inside `setView` and `initialState`.** Rejected on `state.ts`'s stated invariant: every transition is a pure function of the battle and the state before it, which is what lets the rules be tested without a DOM.
- **Accepting the flash before the deferred module runs.** Rejected: nothing paints the viewer's ground until the module has run, so it is a full-screen flash, and it lands on precisely the viewer who cared enough to pick a view. (With the notice moved to the DOM by [#130](https://github.com/NullCoderException/marchpast/issues/130) the ground is painted by `--st-ground` on the root rather than by the notice; the flash and the fix are the same either way.)
- **A palette table inlined in `index.html`'s head**, to kill that flash synchronously. Rejected: it is a fifth hand copy of the values, in the one file that cannot import anything.
- **The library following the view.** Out of scope on map [#121](https://github.com/NullCoderException/marchpast/issues/121) and unchanged here: the library has one look, the brand's.

## Consequences

- **A view supplies nothing new; the surface is derived.** One exported `surfaceOf(view)` maps the palette to the surface's tokens: `--st-ink` from `palette.ink`, `--st-ground` from `palette.paper`, `--st-sunk` from `palette.land`, `--st-rule` from `palette.ink` at 55%, `--st-edge` from `palette.letterbox` for the page ground, and `--st-face` from the view's face. `color-scheme` is derived from `palette.paper`'s luminance and set directly rather than as a custom property.
- **`--st-parchment` becomes `--st-ground`**, because a token named for parchment holding indigo is a name that lies — the same reason `style.ts` became `anatomy.ts`. Only `player.css` is renamed; `library.css` keeps its own names and its own values, which are the brand's to settle.
- **The values stop being copied.** `player.css` keeps every rule it has and carries no value; `index.html`'s inline `<style>` takes `--st-edge`. `library.css` keeps a declaration of its own because the library has no view, but `.st-library-back` comes off that shared rule: the `← All battles` link only ever appears on the player's control strip, on the error path, so it must inherit the strip's tokens rather than declare the plate's.
- **The properties are written on `document.documentElement`, once per switch.** Not per frame, and not on a player root, because `index.html`'s body ground wants them too and the library is a different route in `main.ts`, so nothing leaks.
- **The surface takes the view's face and keeps its own sizes.** A switch may reflow the strip and cost the plate a line of height; that is accepted, and it is bounded by the plate being re-fit on resize already.
- **`color-scheme` is what makes a native `<select>` survive a dark view.** The three choosers are native `<select>`s whose popup the operating system draws, not the page: without it the night plate opens a light list from a dark strip. It fixes the details panel's scrollbar and the native focus rings in the same stroke.
- **The view is remembered; nothing else is.** One module, `src/player/rememberedView.ts`, exports `openingView()` and `rememberView(id)`, both wrapped in `try`/`catch` because storage throws outright in some private modes and a themeless player beats a crashed one. `setView` stays pure, `initialState` takes the opening view as an argument, `main.ts` reads and `player.ts` writes. A stored id no view carries needs no handling: `viewById` already falls back to the default. This supersedes map [#36](https://github.com/NullCoderException/marchpast/issues/36)'s "the chooser never remembers"; the level, the speed, the clock and the open card stay per-visit, and `state.ts`'s doc comments are amended to say the view is now the exception.
- **`rememberView` writes two keys: `marchpast.view` and `marchpast.ground`.** The second holds the resolved `letterbox` colour so that three synchronous lines in `<head>` can set `--st-edge` before first paint, copying no palette and knowing no view ids. A stale ground after a palette edit is wrong for one paint and heals on the next switch. The keys are named for the new name because they are new and durable; the `st-` class prefix stays as ADR-0020 decided, class names not being user-visible strings.
- **The opening view is the remembered one, else the default, and its face blocks the first frame.** This **amends ADR-0021**, which fixed that clause as *the default view's* face. The cost is unchanged — one face still blocks first paint, it is simply not always the same one — and every other face still prefetches at idle, and a switch still waits rather than drawing in a fallback.
- **The no-battle notice takes the opening view** rather than `DEFAULT_VIEW`, and takes it as **DOM text on the surface's tokens** rather than as a plate painted in a palette. [#130](https://github.com/NullCoderException/marchpast/issues/130), resolved two minutes after [#127](https://github.com/NullCoderException/marchpast/issues/127) and read afterwards, moved the notice off the canvas entirely, because a heading drawn with `fillText` is silent to a screen reader and a battle that fails to load is the worst place on the page for that. The two decisions agree on the substance, and the DOM notice is the better host for this one: it is themed by `surfaceOf` automatically, with no palette lookup of its own, and the three synchronous `<head>` lines set its tokens before the deferred module runs. So ADR-0014's clause that the notice is *"the only place outside the drawing passes that reaches for one"* is retired outright rather than relocated — after this there is no non-drawing code reaching for a palette at all. On the library route there is no opening view, and the library loads its own face.
- **The boundary.** Themed: the control strip and every control on it, the Picker and the error-path library link included; the details panel and its sources table; the page ground. Never themed: the library page. There is no header and no back link on the player page to decide about — the page is a `<canvas>` and a `#controls`, and nothing else.
- **Atlas's surface is identical to the chart plate's**, because Atlas spreads `CHART_PLATE.palette`. Switching to Atlas changes nothing outside the canvas, and that is correct rather than a defect: Atlas is the same aesthetic, and it is the picture that differs.
- **The screenshot rule is restated, not deleted: the canvas is the whole *picture* in that view.** The claim that it is the whole *view* goes. The build-time still renderer and the social card ([#126](https://github.com/NullCoderException/marchpast/issues/126)) stay canvas-only in the default view and are unaffected by anything here.
- **The derivation is conformance-tested over `VIEWS`**, on contrast rather than layout: text at 4.5:1 or better against the strip's ground and against the hover fill, and the rule at 3:1 or better against the ground. It earns its place on the *derived* values specifically — a view guarantees its own ink on its own paper, but nothing guarantees ink at 55% against paper, or ink on `land` under a hovering pointer. Both existing surfaces clear it today, so it locks what is already true and makes a fourth view fail loudly instead of shipping an unreadable strip.
- **ADR-0014 stands superseded in two clauses**: that the view stops at the canvas edge, and that the notice reaches for the default view's palette as the only place outside the drawing passes to do so. Everything else it decided holds, including the clauses ADR-0021 left standing: the view as a per-frame argument to `render`, the glyph's two halves, the scratch canvas the engaged cloud is composited on, and a glyph never learning a compass bearing.
- **Two questions are handed on rather than settled here.** Whether the view chooser stays a `<select>` or becomes a drawn control belongs to [#137](https://github.com/NullCoderException/marchpast/issues/137), against a drawing; `color-scheme` is what lets it stay a `<select>` in the meantime. And whether the derivation is right for the staff map is [#137](https://github.com/NullCoderException/marchpast/issues/137)'s to test — if it is not, that ticket comes back and cuts a `surface` hand against a drawing, which ADR-0021 names as the expected path rather than a failure.
