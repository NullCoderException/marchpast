# The site reads no operating-system preference, and the surface declines forced colours

*Amended 2026-09-07 on [#137](https://github.com/NullCoderException/marchpast/issues/137), which placed `forced-color-adjust: none` on `.st-controls` and `.st-details` and looked. The split predicted below is there — the canvas keeps the view's parchment, because forced colours reach CSS-painted DOM and never a `<canvas>` or an `<img>`, while the strip flips to the system palette — but the opt-out's **effect** is unconfirmed: Chrome's emulated forced-colors did not restore the author's ground even with the property set on every element in the strip. Someone must look at the built page in real Windows High Contrast before v0.3 ships, which is [#141](https://github.com/NullCoderException/marchpast/issues/141)'s (**ADR-0030**).*

Nothing in `src/` or `index.html` reads a user-preference media query, and after this decision nothing will. Two were on the table — `prefers-reduced-motion`, noticed and set aside by [#130](https://github.com/NullCoderException/marchpast/issues/130) as the same class of question but not the unit card's, and `prefers-color-scheme`, handed here by [#153](https://github.com/NullCoderException/marchpast/issues/153) so the family would be answered in one sitting rather than half-answered in a ticket about authoring. A third that neither ticket saw, `forced-colors`, is the only one where doing nothing leaves a page visibly broken, and it is the one that gets a rule. Decided on [#160](https://github.com/NullCoderException/marchpast/issues/160).

**Every motion in Marchpast is requested.** There is not one `transition`, `animation` or `@keyframes` in `player.css`, `library.css` or `index.html`, so the only motion in the product is ADR-0002's linear tween between phase snapshots. `initialState` opens with `playing: false`, and `jumpNext`, `jumpPrevious` and `scrubTo` set the clock directly so the loop draws a single frame — a seek **cuts**, it never tweens. A viewer who never presses play never sees a pixel move, so `prefers-reduced-motion` has no unrequested motion to suppress. What it would suppress instead is the product: ADR-0002 weighed *"static phases: units jump at phase boundaries"* and rejected them as *"the slideshow the concept doc set as the floor"*, so honouring the query by cutting would ship the explicitly-rejected picture to the viewer who asked to be treated with care. The unmoving path through a battle already exists as first-class controls — the phase-jump buttons cut, the caption band carries each phase's words and the details panel its notes and references — and it is written down here because from the code alone this decision is indistinguishable from an oversight.

**A view cannot be derived from two values.** There are three views and a fourth coming ([#139](https://github.com/NullCoderException/marchpast/issues/139)); `prefers-color-scheme` has two. Mapping one to the other needs a table of which views are dark, which is exactly **the code counting aesthetics** that ADR-0021 forbids and that #153 already used to kill the weaker "a battle may suggest an aesthetic" variant. The night plate is not the chart plate inverted, it is a different chart with its own palette, and a first-time visitor deriving it from an operating-system setting would meet a battle on black paper while the social card, the library stills and the README all show the chart plate. The cost of refusing is real and accepted: since ADR-0023 the surface *is* chrome, so a dark-OS viewer gets a bright page. That is right anyway — the content is a light paper plate, and darkening the frame around a bright picture worsens glare rather than easing it.

**The library follows nothing either, and it needs a reason of its own.** Every argument above is about views, and the library has none: it is a page of text and links under its own hard-coded palette (`--st-parchment: #efe3c6` on `--st-ink: #2b2418`), real chrome where a dark mode is the most conventional expectation on the web, and none of the picture-of-paper reasoning reaches it. It still does not follow, because after the paragraph above the player *cannot*, and a library that did would make the site read the preference on the front door and ignore it on the very next page — a sharper inconsistency than never reading it, and a dark front door handing straight off to a bright chart plate. It would also need a second brand palette, which [#135](https://github.com/NullCoderException/marchpast/issues/135) closed without one. So the rule is one sentence for the whole site rather than a rule per page.

**`forced-colors` is the member that earns a rule.** Windows High Contrast overrides CSS colours on the DOM and cannot touch a `<canvas>`, and the break has an address: `.st-key-row` in the details panel is a `<canvas>` sample (`.st-key-sample`, drawn in the view's own glyph and pens, [#86](https://github.com/NullCoderException/marchpast/issues/86)) sitting beside a `<span>` word (`.st-key-word`). The word would flip to system colours and the sample four pixels away would not, splitting a single row — the *"two applications bolted together"* failure ADR-0023 rejected, except imposed rather than chosen. So the surface takes `forced-color-adjust: none`, and plate and strip stay one object.

## Considered options

- **Reading `prefers-reduced-motion` and cutting phase to phase** (rejected): it ships ADR-0002's explicitly rejected slideshow to the viewer who asked for care, and the cutting path already exists as the phase-jump buttons.
- **Reading it and opening paused** (rejected): `initialState` already does, so it is a no-op with a code cost and a false claim of compliance.
- **Reading it and seeding a slow speed multiplier** (rejected): slower motion is still continuous motion, for longer. It helps nobody the query is for.
- **Making reduced motion a visible control on the strip** (rejected): the phase-jump buttons and the caption band are that control, and a second one that duplicates them earns nothing.
- **`prefers-color-scheme` seeding the opening view**, between the remembered choice and the default (rejected): it requires the code to know which views are modes, which ADR-0021 forbids.
- **The surface honouring the operating system while the picture does not** (rejected): the split ADR-0023 abolished when it published the palette to `document.documentElement`. Closed on #153 and not reopened here.
- **A dark library from a second brand palette** (rejected): #135 closed the brand without one, and it lands a dark front door on a bright chart plate.
- **Letting forced colours land on the DOM and leaving the canvas alone** (rejected): today's behaviour, and the split key row above.
- **Opting out only the picture-adjacent parts** — the page ground and the key rows — while the control strip takes system colours (rejected): it moves the seam inside the surface rather than removing it.
- **A forced-colors view synthesized from `Canvas`, `CanvasText` and `Highlight`** (rejected): a view the code generates rather than a designer authors, proposed before the third view is even drawn. It is nonetheless the honest repair if the opt-out is ever reversed, which is what makes this decision hard to reverse: undoing it does not restore a default, it returns the broken row and leaves this as the only real fix.

## Consequences

- **`forced-color-adjust: none` on the surface is the whole code cost of this ADR.** [#137](https://github.com/NullCoderException/marchpast/issues/137) places it, because it is drawing that surface against a drawing and can look at the page under High Contrast while it does — **nobody has yet viewed this page in that mode.** That does not put the decision in doubt: the key row's split is structural, a canvas beside a span, not a matter of how it looks.
- **Declining forced colours does not drop below a contrast floor, it holds one.** ADR-0023's derivation is conformance-tested over `VIEWS` at 4.5:1 for text against the strip's ground and the hover fill, and 3:1 for the rule.
- **Colour carries meaning here**, which is what makes the opt-out defensible rather than dismissive: each side's ink is taken by roster order, so ink *is* the side, and no forced palette can reach the canvas that draws it.
- **ADR-0023 gains an amendment line. ADR-0002 does not** — this decision declines to change the tween, and declining to move an ADR is not movement.
- **The glossary gains three clauses.** **Surface**: it holds the view's inks whatever the operating system says, and declines forced colours because the picture cannot follow one. **Library**: one look, the brand's, following neither a view nor the operating system. **Controls**: a phase jump cuts where playback tweens — the fact the unmoving path rests on, which the glossary did not state anywhere.
- **Two reopening triggers, and nothing short of them reopens this.** For motion: **motion nobody pressed play for** — an auto-playing library still, a details panel that slides, animated furniture in a view, or a transition on a view switch. #137 and #139 are each live candidates to introduce one, and both have been told. For colour: **the site gaining a page that is neither a picture nor the brand's**.
- **#141 carries the reduced-motion claim into the `ready-for-agent` issues**, so the unmoving path ships as a stated affordance rather than an accident of the controls.
- **No schema change, no validator rule, no field.** ADR-0014's clause that a battle file names no view is untouched, and #153's glossary sentence — *"no operating-system preference chooses one"* — **stands tested rather than inherited**: it was written into `CONTEXT.md` by #159 ahead of the ticket that was to decide it, and this is the reasoning it was owed.
